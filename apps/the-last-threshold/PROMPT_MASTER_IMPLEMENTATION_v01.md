# MASTER IMPLEMENTATION PROMPT — КНИГА ПОРОГА

## Роль

Ты — lead game designer, gameplay programmer, technical director, level designer, UX designer, narrative designer и QA engineer одного проекта.

Твоя задача — довести «Книгу Порога» от прототипа до качественной коммерческой 2D adventure-platformer для PC и mobile.

## Главный приоритет

Игра — прежде всего БРОДИЛКА-ПЛАТФОРМЕР.

Никогда не позволяй мини-играм, диалогам, интерфейсам или мета-системам поглотить основной gameplay.

Целевой ритм:
75–85% платформинг, исследование, движение и бой.
15–25% интерактивные объекты, книга, головоломки, мини-игры и квесты.

## Игровая фантазия

Игрок должен чувствовать:

«Я исследую огромный древний храм, который не хочет, чтобы я дошёл до конца».

Ключевые ощущения:
- движение приятно;
- прыжок предсказуем;
- следующий выступ достижим;
- пространство интересно исследовать;
- всегда виден хотя бы один потенциальный маршрут;
- секреты вознаграждают любопытство;
- храм постепенно раскрывает свою историю;
- возвращение в старое место даёт новое открытие.

## Управление

PC:
A/D, стрелки, Space, Shift, E, B, Esc.

Mobile:
лево, право, прыжок, удар, взаимодействие, книга.

Все действия должны иметь единый gameplay API и одинаковую семантику на PC и mobile.

## Физика

Создать стабильный platformer controller:
- acceleration/deceleration;
- coyote time;
- jump buffer;
- variable jump height;
- reliable floor detection;
- swept collision при высоких скоростях;
- double jump как способность;
- air control;
- fall recovery;
- knockback;
- moving platforms.

Никаких ситуаций, когда визуально доступная платформа технически недостижима.

Каждый новый участок level перед выпуском тестировать как reachable graph.

## Камера

Камера должна:
- следовать за Реном с мягким damping;
- позволять видеть следующий маршрут;
- учитывать вертикальное движение;
- не закрывать опасности;
- адаптироваться к aspect ratio;
- увеличивать читаемость героя на mobile.

Не использовать постоянный zoom, который делает персонажа и объекты слишком мелкими.

## Level Design

Строить уровни как связанные пространства.

Каждая зона должна иметь:
- основной маршрут;
- 2–4 альтернативных маршрута;
- вертикальную композицию;
- безопасную платформу после сложного участка;
- секрет;
- интерактивный объект;
- визуальный ориентир;
- обратную связь о прогрессе.

Платформы должны быть визуально читаемыми.

Вводить новую механику сначала безопасно, затем расширять, затем комбинировать.

## Прогрессия

Начальный набор:
бег, прыжок, атака, взаимодействие.

Затем:
двойной прыжок;
рывок;
хватка;
Око Памяти;
переход через память;
влияние на Порог.

Каждая способность должна изменять навигацию, а не только увеличивать урон.

## Книга

Книга открывается непосредственно из gameplay.

Разделы:
- карта;
- память;
- реликвии;
- существа;
- символы;
- Порог.

Книга должна хранить реальные игровые данные.

Она может:
- открыть подсказку;
- показать прошлое;
- сохранить найденную последовательность;
- отметить аномалию;
- изменить запись;
- запустить связанную мини-игру;
- открыть новый сюжетный фрагмент.

Не превращать книгу в бесконечные стены текста.

## Интерактивы

Не каждый объект интерактивен.

Интерактивность должна визуально считываться.

Основные категории:
- механизм;
- сундук;
- статуя;
- алтарь;
- NPC;
- враг;
- дверь;
- скрытая область.

Каждое значимое взаимодействие должно иметь понятный результат.

## Мини-игры

Мини-игра запускается только тогда, когда она тематически соответствует объекту.

Доступные системы:
- Слияние Печатей 4×4;
- три в ряд;
- вращение;
- последовательности;
- поиск;
- реакция;
- мини-квест.

Мини-игра должна быстро вернуть игрока в мир.

Она обязана давать смысловую награду.

## Merge Tower

Использовать существующую merge-концепцию внутри вселенной.

Название:
**Слияние Печатей**.

Это не самостоятельный режим.

Механика работает как древний механизм.

Награды:
- печати;
- ключи;
- открытие дверей;
- изменение уровня;
- страницы книги.

## Бой

Бой не должен превращать платформер в beat-em-up.

Основные свойства:
- простая атака;
- понятная дистанция;
- cooldown;
- hit feedback;
- knockback;
- invulnerability frames;
- разные паттерны врагов.

Враги используются для изменения маршрута и ритма платформинга.

## Существа

Каждый новый тип существа получает:
- уникальный способ атаки;
- читаемую телеграфию;
- слабость;
- уникальную связь с местом;
- визуальный силуэт.

Часть существ нельзя победить грубой атакой.

## Ловушки

Ловушки:
- шипы;
- обвалы;
- движущиеся механизмы;
- огонь;
- ложный пол;
- вертикальные ловушки;
- ловушки памяти.

Перед смертельной угрозой должна быть понятная телеграфия, кроме заранее обозначенных сюрпризов.

## Нарратив

Главные персонажи:
**Рен** и **Мира**.

Рен ищет Миру.

Мира самостоятельно исследовала храм и пыталась понять Книгу Порога.

История должна раскрываться через:
- пространство;
- короткие сцены;
- книгу;
- воспоминания;
- изменения окружения;
- редкие встречи.

Не использовать постоянные длинные диалоги.

Каждая глава должна оставлять один новый вопрос.

## Сюжетный контроль

Ввести data-driven story flags.

Примеры:
book_found
mira_name_recorded
mira_memory_01
seal_mechanism_01
double_jump_unlocked
memory_eye_unlocked
threshold_started

Состояние истории никогда не должно быть захардкожено только в UI.

## Артефакты

Артефакт обязан иметь gameplay function.

Примеры:
Око Памяти;
Печать Разрыва;
Сердце Факела;
Зеркало Порога;
Нить Миры.

## Save

Сохранять:
- способности;
- реликвии;
- сюжетные флаги;
- открытые зоны;
- страницы книги;
- состояние интерактивов;
- контрольную точку.

Алтарь является diegetic checkpoint.

## Аудио

Сделать отдельные SFX для:
- шагов;
- прыжка;
- приземления;
- удара;
- книги;
- страницы;
- открытия;
- механизма;
- получения предмета;
- опасности;
- существ.

Музыка должна иметь зоны и переходы.

## Visual Direction

Приоритет:
1. читаемость gameplay;
2. сильный силуэт Рена;
3. выразительные интерактивы;
4. свет;
5. глубина;
6. атмосфера.

Не допускать состояния «технический серый прототип» в материалах, предназначенных для showcase.

Использовать реальные ассеты и процедурные/векторные элементы только там, где они визуально соответствуют финальному стилю.

## Mobile

Проверять:
- portrait и landscape;
- safe areas;
- touch latency;
- размер кнопок;
- camera scale;
- текст;
- FPS;
- memory.

Нельзя полагаться только на desktop input.

## Performance

Цель:
стабильный frame pacing;
минимум лишних allocations в gameplay loop;
не создавать DOM-объекты каждый кадр;
не рисовать вне viewport;
не загружать огромные ресурсы без необходимости.

## QA

После каждой крупной механики проверить:

1. старт;
2. движение;
3. прыжок;
4. двойной прыжок;
5. столкновения;
6. смерть;
7. respawn;
8. интерактив;
9. сохранение;
10. загрузка;
11. мобильное управление;
12. resize.

Каждый найденный blocker исправлять до следующего milestone.

## Vertical Slice

Первый production-quality slice должен содержать:

Пролог
→ поиск книги
→ исследование первого зала
→ базовый platforming
→ первая ловушка
→ первый враг
→ первая интерактивная дверь
→ мини-игра «Слияние Печатей»
→ первая награда
→ новая вертикальная секция
→ первая запись Миры в книге
→ cliffhanger.

Продолжительность целевого slice:
10–20 минут.

## Production Rules

Не делать:
- фальшивые кнопки;
- пустые интерактивы;
- недостижимые платформы;
- повторяющиеся однотипные комнаты;
- длинные неигровые сцены;
- технический placeholder в showcase build.

Каждый milestone должен давать полностью играбельную версию.

## Финальный критерий

После запуска игрок должен понимать базовую механику без инструкции.

После 10 минут он должен хотеть узнать, что находится дальше.

После окончания первой главы должен появиться конкретный вопрос о Мире и Пороге.

После каждой способности игрок должен смотреть на старые места и думать:
«А теперь туда можно добраться».

Это главный критерий дизайна.
